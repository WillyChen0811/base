# 设计稿：项目全面同步 v2（两边同时编码不分叉）

状态：设计稿，待用户过目。需求来源：用户 2026-10-15（见 PLAN-projsync.md 末尾「新需求」各节）。现有 projsync（手动、只交换已提交分支到对方命名空间、对话目录补齐）是 v1，本稿在它之上扩展。

## 一、已确认的需求
1. **同步是自动化脚本**：由 Mac 上的 wgtund 执行，用它对 Ubuntu 接近 root 的权限（SSH 登录用户 chenwy），不经过任何 agent。
2. **范围**：xxyi、base、ai-browser、websubmit、bioflow、biogateway 六个项目的代码与 Git 数据、项目记忆（Claude Code 项目目录：会话 jsonl、子目录、memory/），以及**全部日志**（XXYI/wgtund/钩子日志、Claude Code 会话记录、Codex 会话记录、本地模型 omlx-agent / omlx 会话日志）。
3. **脚本能处理的直接处理，不打扰任何人**：能快进就快进；没有分叉或能干净合并就直接合并；记录与日志按规则补齐。
4. **脚本处理不了的才交给 agent，由用户指定 agent**：没提交的改动由那台设备上的 agent 提交（怎么提交由 agent 决定）；真冲突的合并由 agent 处理。XXYI 要有「按任务类型指定 agent」的能力。
5. **不丢数据**：靠「所有改动都进了提交历史」保证；有提交轨迹就允许直接合并；不做多余备份（打包程序与发布包用户另存）。
6. **时机（用户选 C）**：任何一边有新提交就立即同步，另外定时兜底。

## 二、整体流程（每个项目一轮）
1. **触发**（按第六节第 4 条修订）：每 5 分钟对两边每个项目读一次分支引用指纹和工作区指纹，有变化就跑一轮；网络走 XXYI 当前线路。
   - 手动：设置 > 项目同步里的「立即同步」保留。
   - 同一项目同一时间只跑一轮（已有 errProjsyncBusy）。
2. **交换提交**（沿用 v1）：Mac 的 refs/heads/* 推到 Ubuntu 的 refs/remotes/mac/*；Ubuntu 的 refs/heads/* 取回 Mac 的 refs/remotes/ubuntu/*。只写这两个命名空间，不碰任何本地分支。
3. **逐分支判定**（对两边都有的同名分支；只有一边有的新分支直接在另一边建同名分支）：
   - 两边相同 → 无事。
   - 一边是另一边的祖先 → **快进**落后的一边（见第三节「更新分支的规则」）。
   - 分叉 → 先用 `git merge-tree --write-tree` 在不碰任何工作区的情况下试合并：
     - 干净 → 用 `git commit-tree` 生成合并提交（两个父提交，提交信息写明「XXYI 自动合并 mac/<分支> 与 ubuntu/<分支>」），然后两边都快进到这个合并提交。
     - 有冲突 → **交给 agent**（第四节）。
4. **未提交改动**：判定之前先看两边该项目当前检出分支的工作区。有已跟踪文件的改动或未跟踪文件（按 .gitignore 过滤后）→ **交给该设备的 agent 提交**（第四节），这一轮里该分支先只交换、不更新，等提交完成再触发下一轮。
5. **记录与日志补齐**（第五节）。
6. **结果**：写同步日志（每轮一条：项目、每分支动作、耗时、交给 agent 的事项），设置 > 项目同步面板显示每个项目的上次结果与待处理事项。

## 三、更新分支的规则（保证不丢数据、不打断正在干活的人）
- 分支**没被任何工作区检出**：直接 `git update-ref`（只允许更新到当前值的后代，否则拒绝）。
- 分支**正被检出**且工作区干净：在该工作区执行 `git merge --ff-only <目标>`（会同步更新文件）。
- 分支正被检出且工作区**不干净**：不更新，先走「未提交改动」流程。
- 任何情况下都**不做**强制更新、reset、checkout 切分支、删除分支；拒绝更新时只记日志和待处理事项。
- 正在 rebase/merge/cherry-pick 中的仓库：整个项目这一轮跳过，记原因。

## 四、交给 agent 的事（用户指定 agent）
- 两类任务：「提交未提交的改动」（在该设备、该仓库）和「解决合并冲突」（在哪台设备做待定，建议另开 worktree 不动正在干活的工作区）。
- **指定 agent**：设置里按任务类型配置默认执行会话（例如 提交→mac:omlx1，冲突合并→ubuntu:某会话），也可以选「每次问我」。XXYI 用现有消息通道派活（kind=request，正文自包含：仓库、分支、两边提交、冲突文件列表、要求做完提交并回复）。
- 指定的 agent 忙 → 排队；不在线 → 在面板与菜单栏提示用户；agent 回复失败或超时 → 失败报告交给用户。
- agent 完成后（收到 kind=code 回复）自动触发该项目下一轮同步。

## 五、记录与日志
- 目录（每台机器各自的位置，两边互相补齐；对方的内容放在自己这边的「对方」子目录，不和本机文件混在一起，避免同名覆盖）：
  - Claude Code 项目目录（v1 已有，按项目路径推目录名）。
  - Codex 会话：~/.codex/sessions/
  - XXYI/wgtund 日志：Mac ~/.xxyi/*.log、*.jsonl；Ubuntu ~/.xxyi-support/*.log
  - 本地模型：~/.omlx-agent/logs/
- 规则沿用 v1：只有一边有 → 拷过去；相同 → 跳过；一边是另一边的前缀（只追加）→ 长的覆盖短的；其他 → 冲突，两边都不动、记入待处理（日志冲突不交 agent，只报告）。永不删除。

## 六、用户已定（10/15，覆盖上文对应内容）
1. **同步所有分支**：只有一边有的新分支也同步过去。
2. **合并冲突由用户手动处理**：在 XXYI 控制中心的「项目同步」里显示冲突（项目、分支、两边提交、冲突文件），由用户手动处理；冲突**不**交给 agent。第四节里「解决合并冲突」这一类任务取消。
3. **未提交改动：至少 20 分钟没有变动才允许自动提交**。判定「没有变动」：该仓库工作区（已跟踪文件改动 + 未跟踪文件，按 .gitignore 过滤）的指纹连续 20 分钟不变。不满 20 分钟的，这一轮该分支只交换、不更新，等下一轮。提交仍按第四节由那台设备上用户指定的 agent 做（怎么提交由 agent 决定）。
4. **检测间隔至少 5 分钟**（不再做 10 秒轮询）：每 5 分钟检测一次两边是否有新提交/未提交改动，有就跑一轮；手动「立即同步」保留。**网络走 XXYI 当前的线路配置**（hosts.json 里主机当前选中的线路），不另设线路。
5. **消息代码同步并入项目同步，并把状态反馈给 agent**：kind=code 消息不再自己做单向同步；发送前触发该项目一轮同步并等它完成，把同步结果（成功、哪些分支快进/合并、冲突待用户处理、未提交改动等待中）原样反馈给发送消息的 agent。
6. **两边都用 ~/Documents/codes/ 下的仓库**。注意：Mac 上 xxyi 现在在 ~/xxyi-work/xxyi（omlx 会话的工作目录、build.sh、XXYI.app 路径、hosts.json 的 support.repos/projsync 都指向这里），base 在 Mac 有两份（~/xxyi-work/base 与 ~/Documents/codes/base）——需要一次迁移：把 Mac 的 xxyi、base 统一到 ~/Documents/codes/ 下，并改所有引用。迁移步骤另写，执行前给用户过目。

## 八、第 2 项「执行器」的必须要求（来自 Codex 对第 1 项的评审，10/15）
- 携带执行前提：两边完整旧 OID、目标 OID、仓库标识、检出工作区路径、事实版本；AutoMerge 还要保留两个父提交。可放独立执行上下文，不必塞进 BranchAction。
- 区分「不存在」与「读取失败」：空哈希只代表已确认引用不存在；网络、权限、对象缺失等错误不能当成空值。祖先检测和试合并要区分成功、否定、命令失败；失败一律停止，不产生任何写动作。
- 引用更新：更新前确认目标是旧值的后代，并用旧 OID 做比较交换（`git update-ref <ref> <new> <old>`）；创建用「必须不存在」的比较交换。引用变了就停止、重新判定。
- 重新检查所有工作区：包括 linked worktree、unborn HEAD、引用缺失但仍被 symbolic HEAD 指向；多个工作区检出同一分支时拒绝普通更新路径。
- 检出分支只在实际工作区执行快进：更新前重新确认分支、HEAD、索引、已跟踪与未跟踪内容、busy；用 `merge --ff-only`，禁止 autostash、强制覆盖、reset、切分支、删分支；拒绝时保留现场。**检查与写入之间的竞态**：`merge --ff-only` 本身不校验预期旧 OID、也不保证当前仍是预期分支——执行前在同一命令序列里再读一次 `symbolic-ref HEAD` 与分支 OID，和事实版本不一致就停止；同一仓库的同步任务、提交 agent 任务、工作区操作要串行（同步执行期间不派提交任务，提交任务在途时不执行该工作区的分支写动作）。补「检查后、写入前发生切分支或检出变化」的竞态测试。
- 创建分支只建引用：不碰 detached HEAD 的文件、索引、HEAD；目标已存在或被工作区 HEAD 指向时停止。
- 合并绑定精确父提交：不碰工作区地试合并、建提交，验证两个原提交都是新提交的祖先；两边更新前都重新检查；一边成功另一边失败时保留成功结果，重新采集后重试，禁止回退覆盖。
- 提交任务按工作区派发：按设备、仓库、规范化路径去重并跟踪在途任务，防止每轮重复派活；派发前和真正执行前都验证指纹已连续静止 ≥20 分钟。**派发时立即作废依赖该工作区的分支计划**；任务在途期间，禁止执行任何依赖该工作区旧事实的写动作；任务完成、失败或超时后重新采集，再重新判定。
- 冲突只交控制中心：保存分支、双方 OID、冲突文件；不派冲突处理 agent；把「执行出错」和「真实冲突」分开展示。
- 集成测试必须覆盖：事实采集后引用/检出状态/文件变化；创建目标被抢先建立；未跟踪文件挡住快进；一侧成功另一侧失败后重试；祖先检测、引用读取、试合并命令失败时不产生写动作。

## 九、第 3–4 项（自动合并接线、触发器/调度层）的必须要求（来自 Codex 对第 2 项的评审，10/15）
- 自动合并固定父提交的设备顺序：Parents[0] = mac 侧、Parents[1] = ubuntu 侧；提交信息写明 mac、ubuntu 与完整父 OID。
- 合并对象必须先安全传到另一侧，再分别重新检查并快进；一边成功另一边失败时保留成功结果、重新采集，禁止回退。
- 互斥按实际 Git common directory（`git rev-parse --git-common-dir` 的规范化路径）统一加锁，覆盖主工作区、linked worktree、同步、提交任务和受控工作区操作；只按项目名或路径字符串加锁不够。
- 写后复查只能发现「最终仍被检出」，发现不了「检出后又离开」的窗口，不得当作互斥的替代品。
- 引用已写入后出现复查失败、取消或检出竞态（如 ErrCheckedOutDuringUpdate）→ 报告「已写入、现场需确认」，停止该项目后续写操作，不得作为普通未执行失败直接重试。
- 派提交任务立即作废相关计划；在途禁止相关写入；结束后重新采集；派发和执行时都验证静止 ≥20 分钟。
- 冲突与执行故障分开报告；merge-tree 冲突时的 stdout 里有冲突信息，接线时要保留并解析（runGitCode 失败时不能丢 stdout）。

## 十一、总原则（用户 10/15）：识别边界、超出就停
用户原话：「真正的问题在于是否把边界限制在：当发现可能超出工具处理能力时，能识别到边界并防止数据错误。」
- 工具**不追求处理所有情况**。先定义明确的「支持范围」（白名单）；仓库状态完全落在范围内才自动写；任何不认识、不确定、超出范围的状态都判「超出自动同步范围：<原因>」，**不写任何东西**，在控制中心报告，交用户或指定 agent。
- 审查标准随之改为有限的问题：**有没有超出范围的状态被误判为在范围内而被写入**；超出范围的情况不要求正确处理，只要求被识别并停下。
- 支持范围（用户 10/15 确认，实现为写操作前的统一检查）：分支名为合法 UTF-8、已是 NFC 组合形式（允许中文等非 ASCII 字符；常用汉字 NFC 与 NFD 相同），且两边不存在「NFC 规范化后相同但字节不同」的分支名，不满足即判超出范围——不建重复分支；分支是直接引用；该分支没有 mergeOptions 等改变合并行为的配置；没有 sparse-checkout、skip-worktree、assume-unchanged 条目；常规 .git 布局（非独立 git 目录等特殊布局），工作区数量在预期内；子进程环境清掉继承的 GIT_* 变量；Git 版本在已验证范围（≥ 2.38）；工作区干净、无进行中的操作（已实现）。
- 第 2 项已实现的各类具体防护保留（多一层保险），但不再继续为边角情况追加专门处理；此后发现的边角一律先归入「超出范围就停」。
