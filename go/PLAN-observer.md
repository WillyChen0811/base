# 观察者：独立于会话汇报的状态与送达确认（设计稿，待用户确认）

> 2026-10-26：仅留作历史记录。协助/消息/审批已于 2026-10-26 拆除，证书库 xxyica 与审批队列 approval 保留未接线。

用户 10/15 的要求：消息中心要掌握所有会话动态；发出的消息要能确认对方收没收到、告诉发送者成败；发送者可撤回并留记录；不靠 token（脚本，不是 agent 常驻）；时限不动。现状问题：状态只靠会话钩子自报，钩子静默失败就既不知道在不在、也不知道忙不忙，送达只等对方钩子回执。

## 1. 观察者做什么
每台机器（Ubuntu、Mac）一个观察循环，每 1 秒读一次本机 tmux，把「会话状态表」报给 XXYI。零 token，纯本地读取。

每个 tmux 会话的事实：
| 事实 | 来源 |
|---|---|
| 会话/窗格存在、前台程序（claude/codex/bash/…） | `tmux list-panes -a` |
| 前台程序是否退出、窗格是否已死 | `pane_dead`、`pane_current_command` |
| 屏幕是否在变 | `capture-pane` 内容指纹 |
| 后台子进程（后台 shell 等） | 窗格进程树 |
| 会话记录最后几条（claude：`~/.claude/projects/*/*.jsonl`；codex：`~/.codex/sessions/`） | 读文件尾部 |

## 2. 状态判定（10/15 实验结论）
- **推理中/空闲**：屏幕有 `esc to interrupt` ⇔ 忙；会话记录最后一条助手消息 `end_turn` ⇔ 空闲。两者一致取之，不一致标「存疑」。
- **等工具/子代理**：记录里有 `tool_use` 没有对应 `tool_result`。
- **后台任务**：进程树里有 claude 的非 xxyi-msg 子进程。显示为「空闲（后台 N 个）」。
- **会话不在**：tmux 里没有该会话 → 失联，不看钩子。
- 无记录文件的程序（普通 shell）：只看屏幕指纹变化 + 前台命令。
- 钩子仍保留，只做加速（立刻更新），不再决定状态。
- 已知局限：只测了 Claude Code；codex 的屏幕文字与记录格式要单独实测；Claude Code 升级可能改文案 → 文案找不到时自动降级为只用记录文件；「安静地想很久」未测。

## 3. 在线名单
状态字段：`在线（忙/闲/等工具/存疑）`、`失联`、`未报到`（会话在 tmux 里、但还没任何上报 → 观察者仍给出事实状态，不再显示 unknown）。
- 失联显示（用户 10/15 定）：失联期间灰显「失联」，**超过 1 分钟仍未恢复就从名单里直接消失**；之后它再出现按新会话处理。
- 观察者放进 `wgtund`（用户 10/15 定），随它启动。Ubuntu 侧同样跑一份 wgtund 观察模式（只观察本机 tmux、上报到 XXYI，不开其它服务）；具体 Ubuntu 侧进程形态实现时先查现状再提方案。

## 4. 发送、送达、撤回
消息状态机（每步写记录，不覆盖）：
`排队 → 已注入 → 已送达（屏幕出现了正文）→ 已开始处理 → 已回复`
`排队/已注入失败 → 重试中 → 失败（完整报告交 XXYI）`
`排队 → 已撤回（发送者撤，记录保留）`

- **送达确认**：注入后观察者看目标窗格屏幕是否出现这段文字（或记录文件出现这条用户消息），不再只等钩子回执；两者任一满足即「已送达」。
- **收件人不存在/失联**：不静默排队，也不替发送者决定。立即把「收件人不在线」告诉发送者，消息保持「排队」；是否继续等、是否撤回、要不要向 XXYI 查询状态，由发送者自己判断，所以必须给发送者两个随时可用的手段：查询（状态、失败原因、收件人当前状态）和撤回（`xxyi-msg` 命令与 MCP 工具都要有）。XXYI 不自动撤回、不自动放弃（时限到了的失败报告照旧）。
- **撤回**：只发送者可撤，仅限未送达前；已注入终端的无法撤回，界面标明「已送达，无法撤回」。撤回后消息保留在记录里，状态「已撤回」，注明时间和撤回人。
- 发送者随时能查自己发出消息的状态与失败原因（`xxyi-msg` 命令与 MCP 工具都要给）。
- 时限（确认 30 秒、重试 30 分钟、等回复 2 小时）不改，不做界面。

## 5. 实现拆分（等 Mac 上 omlx1 做完界面，再派 Ubuntu 的 omlx 按顺序做，每步测试 + Codex 审）
1. 观察循环 + 状态判定 + 会话状态表（纯函数 + 用假 tmux 输出/假记录文件的测试）。
2. 接入在线名单（`who`/`/msg/who`），钩子降为加速。
3. 送达确认改为「屏幕/记录出现正文」。
4. 撤回与状态机（含记录保留）、发送者查询。
5. 收件人不在线的即时反馈。
6. Mac 界面：消息面板显示新状态、撤回按钮（带字）、失联显示（交给界面执行者）。

## 用户要求（10/15，消息这一块最重要的事，逐条记录，未完待续）
1. **状态是第一需求，消息要分紧急程度。** 本地模型执行者（omlx）不太能接受打断，所以最需要准确的状态；发消息时要能确认紧急程度、判断是否需要紧急送达。像「要求暂停」这类消息必须马上送达（不能像现在这样排队到对方空闲）；如果有管理能力，甚至可以直接结束对方进程。
   - 实现时要回答的设计问题（待用户定）：紧急级别分几档；「马上送达」在对方忙时具体怎么做（例如先发中断键打断当前轮次再注入，还是只注入不打断）；谁有权发紧急消息、谁有权结束进程（结束进程是否要用户确认）；结束进程是停 tmux 会话还是只停里面的程序；被打断/结束后如何留记录和告知发送者。
2. **送达通道的优先级（用户 10/15 纠正：设计走偏了）。** 原本的要求是：**能通过其他通道送达的，就不要往终端里打字；只有没有别的通道时，才用「注入终端」这条兜底。** 现在的实现把「注入终端」当成了唯一的送达方式，结果 10/15 用户在 ubuntu:xxyi 终端里打字打到一半，自动批准的消息被注入，和用户没打完的字拼成了一条输入（用户原话：「还好你是 opus，不然就乱套了」）。问题的根子不是「要等用户停止打字」，而是不该默认走终端。
   - 可能的非终端通道（待实测确认，未验证前不要当事实用）：会话自己的 MCP 工具主动取信（xxyi_inbox）；Claude Code 钩子把消息作为附加上下文交给 agent（例如工具调用前后、一轮结束时的钩子输出），这样对方忙时也能在下一个工具调用间隙收到，不需要打断、也不碰用户的输入框；本地模型会话与 Codex 会话各自支持哪些钩子要分别核实。
   - 实现时要回答的设计问题（待用户定）：每类会话（Claude Code / Codex / omlx 本地模型）的首选通道和兜底通道；什么情况下才允许注入终端；紧急消息（要求 1）走哪条通道；送达确认怎么做（非终端通道下，对方「已读到」如何回执）。

## 实验：钩子能否不经终端送消息（10/15，Claude Code 2.1.300，`claude -p --model haiku` + 临时 --settings，未动任何正式配置）
1. **工具调用后（PostToolUse，hookSpecificOutput.additionalContext）**：钩子输出的一段「XXYI 消息」被 agent 收到并照做（在回答里写出了暗号）。→ 对方**忙的时候**，可以在下一次工具调用之后把消息交给它，不打断、不碰输入框。
2. **工具调用前（PreToolUse，permissionDecision=deny + 原因）**：有「暂停」标记时，所有工具调用都被拦下，后两条命令没有执行——**机械上的暂停有效**。但 agent 明确说「这段文字出现在工具返回的错误里，不是你直接发给我的消息，所以我没有照它停下来」，即它不把钩子里的文字当成用户指令。→ 紧急暂停可以靠「拦住工具」实现；但要它按消息内容行事，需要可信来源（例如配合 xxyi_verify 核验，或由用户/指挥的已认证消息）。
3. **一轮结束时（Stop，decision=block + reason）**：agent 本要结束时，钩子把收件箱里的新消息作为 reason 交给它，它继续执行了新任务（跑了 echo world 并报告）。→ 对方**刚空闲时**，可以不往终端打字就把消息交给它。
未验证：交互式会话（非 -p）是否完全相同；本地模型（omlx，同为 Claude Code 外壳）对附加信息的理解是否可靠；Codex 的钩子是否支持同类输出；来源可信度如何表达才会被 agent 采信又不被伪造。
